Pitline

A multi-tenant garage booking platform. Each garage gets a phone-first booking page on its own domain or a free <slug>.pitline.co.uk link, and runs its diary, customers, reminders, messages and invoices at pitline.co.uk. One Next.js app serves every garage, the request host decides which garage, and all data sits in one London Postgres database with row-level security.

Data

Supabase Postgres 17, London

RLS on every tenant table, booking functions in SQL, a btree_gist exclusion constraint against double bookings, Auth with TOTP, Storage.

AI voice desk

Node 22 service on Cloud Run. Answers missed calls for Pro garages over Twilio ConversationRelay with Claude, booking through the agent tool API.

Data model

93 tables in public from 36 migrations, 20 masked views in superadmin, three Storage buckets. Diagrams show keys, the tenant key and the most telling columns.

Tenant key

75 tables carry garage_id

Not null, defaulted from current_garage_id(), cascading from garages. Children use composite keys so a row cannot point into another garage.

RLS

Policies on every tenant table

garage_id = current_garage_id(), which trusts the x-garage-id header only for the service role or a member. anon has no grants.

On the Vercel Hobby plan there is one cron, /api/cron/daily at 11:00 UTC, which queues the day's platform jobs and drains the queue for up to 20 seconds. Booking notifications, HELP answers and missed-call text-backs are drained straight after the request that queued them. Cloud Scheduler runs the super admin's notify job every 5 minutes.

Key flows

The journeys that matter most, step by step.

Security

Trust boundaries, authentication and authorisation, secrets handling and data protection.

Auth

Authentication

  • Staff: Supabase Auth, TOTP mandatory for owners
  • Platform admins: AAL2 on every platform function
  • Django super admin: lockout, TOTP, fresh code per change
  • Car owners: signed manage links, no account
Access

Authorisation

  • RLS on garage_id; garage from host or selected membership
  • Owner, manager, technician roles
  • Booking and job functions for the service role only
  • Support sessions read-only, two hours at most
Machines

Agents and webhooks

  • Agent tokens: peppered HMAC, tool scopes, Pro for Workforce
  • Voice desk: 5-minute signed claim, per-call token
  • Twilio, Stripe, Resend and Cloudflare signatures
  • Cron and drain: bearer secret, constant-time check
Secrets

Where secrets live

Vercel environment variables (Sensitive), GitHub Actions secrets, Google Secret Manager for Cloud Run. No secret uses a NEXT_PUBLIC_ name. Deploys use Workload Identity Federation, not stored keys.

Privacy

Data protection

  • All data and compute in London
  • Registrations kept out of URLs, analytics and logs
  • Stored consent with exact wording; STOP honoured at once
  • Message bodies cleared after 12 months
Abuse

Abuse controls

  • Turnstile and per-IP, per-garage rate limits
  • Idempotency keys on bookings
  • Per-host CSP and frame-ancestors
  • no-referrer on token links
